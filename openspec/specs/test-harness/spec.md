# test-harness Specification

## Purpose
An in-process virtual AirPlay receiver lets every protocol part of this plan be validated
deterministically, without physical hardware or external services, and bidirectionally — the
sender is tested against an independent implementation of the same wire contract.

## Requirements

### Requirement: In-process virtual receiver

The harness SHALL provide a virtual AirPlay receiver that starts inside the test process without
system services, is reachable at an address the test knows, and serves the control endpoints of the
mode it was started in. The multicast responder that makes it discoverable is owned by the
discovery capability, not by this one.

```ruby
Airplay.sync do
  receiver = Airplay::FakeDevice::Receiver.new(
    record: { name: "Studio", model: "AppleTV6,2", features: 7 }
  ).start

  body = Airplay::Session.open(receiver.device) { |session| session.get("/record").body }
  JSON.parse(body) # => {"name"=>"Studio", "model"=>"AppleTV6,2", "features"=>7, "password"=>false}

  receiver.stop
end
```

#### Scenario: Receiver runs with no system services

- **WHEN** a protocol test starts the virtual receiver on a loopback interface
- **THEN** a client connects to it at that address and completes the mode's handshake without
  physical hardware or any background daemon

#### Scenario: Configured record is exposed

- **WHEN** a test configures the receiver's service record, model and capability mask
- **THEN** the receiver exposes that record, and where the discovery capability is present a client
  browsing for it observes exactly those capabilities

### Requirement: Per-mode protocol coverage

The virtual receiver SHALL be extensible with protocol modes — legacy control, pairing and encrypted
control, video play queue, and an audio sink — and SHALL record the traffic it received so tests can
assert on wire content, ordering and timing.

```ruby
receiver.exchanges.last
# => #<struct Airplay::FakeDevice::Receiver::Exchange
#      method="POST", path="/command",
#      headers={"content-type"=>"application/x-apple-binary-plist", "x-test"=>"yes"},
#      body="payload">
```

#### Scenario: Wire assertions

- **WHEN** a test drives a mode and then asks the receiver for the recorded exchanges
- **THEN** the recorded requests expose method, path, headers and decoded body for assertion

#### Scenario: Independent implementation

- **WHEN** a mode's behaviour is asserted
- **THEN** both the client and the receiver must agree on the wire format, and a mismatch fails the test rather than being normalized away

### Requirement: Fault injection

The virtual receiver SHALL support per-test fault configuration covering delayed or absent
responses, dropped or truncated payloads, connection resets, error status codes, authentication
challenges, and corrupted payload bytes. Corrupted authentication tags are added by the pairing
mode that first parses them.

```ruby
receiver = Airplay::FakeDevice::Receiver.new(
  faults: { 1 => { kind: :delay, seconds: 1 } }
).start

Airplay::Session.open(receiver.device, timeout: 0.1) { |session| session.get("/record") }
# raises Airplay::TimeoutError with code :timeout
```

```ruby
Airplay::FakeDevice::Receiver.new(faults: { connection: :reset }).start
# the next request raises Airplay::TransportError with code :connection_lost
```

#### Scenario: Fault is selected per test

- **WHEN** a test configures a delayed response for one request
- **THEN** the client's timeout path is exercised and no other request of that test is affected

#### Scenario: Failure paths are observable

- **WHEN** the receiver is configured to reject authentication
- **THEN** the client raises its documented authentication error rather than retrying indefinitely

### Requirement: Deterministic time

Tests that depend on timing SHALL use an injectable or advanceable clock, so pacing, anchoring and
multi-room tolerance can be asserted without sleeping on the wall clock.

```ruby
clock = Airplay::FakeDevice::FakeClock.new
clock.advance(60)
clock.now # => 60.0
```

#### Scenario: Pacing asserted without wall-clock waits

- **WHEN** a timing test advances the injected clock past a scheduled instant
- **THEN** the sender's behaviour at that instant is observable immediately, with no real-time sleep

### Requirement: Vectors sourced from outside the implementation

Golden wire vectors SHALL be derived from external references or from committed captures, and SHALL
NOT be generated by the implementation under test.

```ruby
# test/fixtures/pairing/hkdf_control_read.bin is captured from the reference implementation
vector = File.binread("test/fixtures/pairing/hkdf_control_read.bin")
assert_equal vector, derive_control_read_key(seed)
```

#### Scenario: A regression cannot redefine the expectation

- **WHEN** a wire-format test runs
- **THEN** it compares against a fixture authored independently of the code path it validates

### Requirement: Opt-in hardware validation

A hardware lane SHALL exist for validating against real receivers, gated by environment
configuration, skipped when that configuration is absent, and recording the device model,
firmware version and outcome of each run.

```sh
AIRPLAY_HARDWARE_HOST=192.168.1.12 \
AIRPLAY_HARDWARE_PORT=7000 \
nix develop -c bundle exec rake test:hardware
```

#### Scenario: Hardware absent

- **WHEN** the hardware lane runs with no receiver configured
- **THEN** its tests skip with a reported reason and the exit status is successful

#### Scenario: Hardware present

- **WHEN** a receiver is configured and the hardware lane runs
- **THEN** the observed device identifiers and outcomes are recorded in the lane output

### Requirement: Discovery in-process mDNS responder double

The test harness SHALL provide an mDNS responder double that advertises configurable service
instances — instance name, service type, SRV target, port, TTL and address family — over the
multicast destinations on an interface usable in tests, without external services, and records
every query it receives with its source and decoded contents.

```ruby
Airplay.sync do
  responder = Airplay::FakeDevice::MDNSResponder.new(
    port: 55_353, interfaces: ["lo0"]
  ).start

  responder.advertise(
    name: "Living Room",
    type: "_airplay._tcp.local.",
    target: "living-room.local.",
    port: 7000,
    txt: { "deviceid" => "AA:BB:CC:DD:EE:FF", "features" => "0x5A7FDFD5,0x3C155FDE" }
  )

  result = Airplay::Discovery::Browser.new(
    port: 55_353, interfaces: ["lo0"]
  ).browse(window: 0.5)

  result.records.first.port # => 7000
  responder.stop
end
```

#### Scenario: Discoverable without system services

- **WHEN** a test starts the responder double with one configured instance and browses
- **THEN** the instance is discovered with no system daemon installed and no external network used

#### Scenario: Received traffic is inspectable

- **WHEN** a test asks the responder double for the traffic it recorded
- **THEN** each entry exposes the source address, the arrival order and the decoded query or answer

### Requirement: Discovery harness fault injection

The responder double SHALL support per-test discovery faults: withholding or delaying an instance's
SRV answer, answering with a TXT record that conflicts with an earlier answer for the same instance,
answering only on IPv6, and dropping a configured fraction of answers.

```ruby
responder.advertise(
  name: "Silent",
  type: "_airplay._tcp.local.",
  target: "silent.local.",
  port: 7000,
  fault: :withhold_srv
)

responder.advertise(
  name: "Lossy",
  type: "_airplay._tcp.local.",
  target: "lossy.local.",
  port: 7000,
  drop: 0.5
)
```

#### Scenario: Withheld SRV answer

- **WHEN** the responder withholds SRV answers for an instance it announced
- **THEN** the browse result contains no record for that instance

#### Scenario: Conflicting TXT answer

- **WHEN** the responder answers the second query for an instance with a different TXT map
- **THEN** the record reflects the newer map once its TTL has replaced the earlier one

#### Scenario: IPv6-only answer

- **WHEN** the responder is configured to answer only on the IPv6 multicast group
- **THEN** the instance is discovered with an IPv6 address

#### Scenario: Dropped answers

- **WHEN** the responder drops a configured fraction of its answers
- **THEN** the browse still returns within its window and the responder's log shows the retry queries

### Requirement: Pairing virtual receiver mode

The harness SHALL provide a virtual receiver mode that performs the HAP pairing handshake — transient with the fixed code and PIN/password — and, once pairing completes, serves an authenticated control session in which every subsequent request is framed and encrypted.

```ruby
receiver = Airplay::FakeDevice::Receiver.new(pairing: { pin: "1234" }).start
store = Airplay::Pairing::CredentialStore.new(directory: Dir.mktmpdir)
Airplay::Pairing::Setup.new(code: "1234", transient: false, store: store).run(connection)
```

#### Scenario: Transient pairing completes with the fixed code

- **WHEN** a test starts the mode and drives a transient pairing exchange
- **THEN** the mode accepts the fixed code and the sender reaches an encrypted control session without hardware or system services

#### Scenario: PIN pairing completes and rejects a wrong code

- **WHEN** a test drives the PIN/password flow once with the accepted code and once with a rejected code
- **THEN** the first exchange yields an encrypted session and the second is answered with the mode's rejection, which the test observes as the sender's authentication failure

#### Scenario: The mode requires encryption after pairing

- **WHEN** a test sends an unframed request after the mode has completed pair-verify
- **THEN** the mode refuses it instead of handling it as a normal control request

### Requirement: Pairing recorded encrypted traffic

The mode SHALL record the traffic of an encrypted exchange and expose, per request, the method, path, headers and the decoded plist body together with the connection it arrived on, so tests can assert on decrypted wire content and ordering.

```ruby
exchange = receiver.exchanges.last
[exchange.method, exchange.path, exchange.plist, exchange.connection]
```

#### Scenario: Decrypted requests are assertable

- **WHEN** a test completes an encrypted session and asks the mode for the recorded traffic
- **THEN** each recorded request exposes its method, path, headers and decoded plist body

#### Scenario: Ordering and connection are preserved

- **WHEN** a test sends parameters and then a teardown, and later opens a second connection
- **THEN** the recorded order matches the received order and each request carries the connection it arrived on

### Requirement: Pairing fault configuration

The mode SHALL support per-test fault configuration for a rejected pairing (wrong code), a `401` challenge on an authenticated request, a corrupted authentication tag, a replayed frame counter, and a receiver that ignores every byte after a rejection.

```ruby
Airplay::FakeDevice::Receiver.new(
  pairing: { faults: { wrong_pin: true, wedge: true } }
).start
```

#### Scenario: A fault affects only the test that selected it

- **WHEN** one test enables the wrong-code fault while other tests in the same run do not
- **THEN** only that test's pairing is rejected and every other test pairs normally

#### Scenario: A rejected pairing can wedge its socket

- **WHEN** a test enables the wedge fault and the sender retries
- **THEN** the wedged socket receives no further bytes and the retry arrives on a separate recorded connection

#### Scenario: Counter and tag faults close the connection

- **WHEN** a test enables the replayed-counter fault, and separately the corrupted-tag fault
- **THEN** each case closes the connection and the test observes the sender's documented failure rather than a handled request

### Requirement: Pairing framing fault configuration

The mode SHALL additionally support per-test faults on the encrypted transport itself: a frame truncated before its declared length is complete, and a frame header declaring a length above the accepted maximum, so the sender's framing bounds are exercised against a receiver rather than only a unit.

```ruby
Airplay::FakeDevice::Receiver.new(
  pairing: { faults: { truncated_frame: true } }
).start
```

#### Scenario: Truncation mid-frame is selectable

- **WHEN** a test enables the truncated-frame fault
- **THEN** the connection ends inside a frame and the sender's session fails instead of waiting for the rest

#### Scenario: An oversized declared length is selectable

- **WHEN** a test enables the oversized-length fault
- **THEN** the sender fails fast without buffering the declared bytes

### Requirement: Pairing clock injection

The mode SHALL accept an injectable, advanceable clock so that the feedback interval and session timeouts are asserted without sleeping on the wall clock.

```ruby
clock = Airplay::FakeDevice::FakeClock.new
receiver = Airplay::FakeDevice::Receiver.new(
  pairing: { clock: clock, feedback_interval: 2 }
).start
clock.advance(2)
```

#### Scenario: Feedback is asserted without a wait

- **WHEN** a test advances the injected clock by the mode's configured feedback interval
- **THEN** the sender's feedback behaviour at that instant is observable immediately

### Requirement: Pairing credential sandbox

The mode SHALL run against a temporary credential directory supplied through the environment override, and no pairing test SHALL read or write the user's real credential location.

```ruby
store = Airplay::Pairing::CredentialStore.new(directory: Dir.mktmpdir)
# the sandbox path is used instead of $XDG_CONFIG_HOME/airplay/devices
```

#### Scenario: Pairing writes only inside the sandbox

- **WHEN** a test completes a long-term pairing against the mode
- **THEN** the credential record appears in the temporary directory with the production modes and nothing is written to the user's configuration directory

### Requirement: Legacy receiver mode

The in-process virtual receiver SHALL be startable in a legacy AirPlay 1 mode that answers the legacy control endpoints — `GET /server-info`, `PUT /photo`, `POST /play`, `POST /scrub`, `GET /scrub`, `GET /playback-info`, `POST /rate`, `POST /stop` and `PUT /setProperty` — from a script supplied by the test, and the started instance MUST serve on one host and port for its lifetime.

```ruby
receiver = Airplay::FakeDevice::Receiver.new(
  legacy: { script: { ["GET", "/server-info"] => { body: Airplay::Plist.dump_xml(info) } } }
).start
```

#### Scenario: Starting the receiver in legacy mode

- **WHEN** a test starts the virtual receiver in legacy mode with a script that answers `GET /server-info` with an XML property list
- **THEN** the receiver is listening on a host and port the test can read, and that request returns the scripted property list

#### Scenario: Legacy control endpoints are answered together

- **WHEN** one legacy-mode instance receives each of the legacy control endpoints in turn
- **THEN** every one of them is answered from the script while the instance keeps its host and port

### Requirement: Legacy receiver mode recordings

Recorded exchanges SHALL expose the request method, the path with its query string, the request headers, and the raw body bytes as received, so a test can assert binary payloads, header values and command targets verbatim.

```ruby
exchange = receiver.exchanges.last
[exchange.method, exchange.path, exchange.headers, exchange.body, exchange.serial]
```

#### Scenario: Recording a binary photo payload

- **WHEN** a `PUT /photo` whose body contains CRLF pairs and bytes above `0x7F` is received
- **THEN** the recorded exchange carries a body byte-identical to what was sent, together with the recorded `X-Apple-Transition` and `Content-Length` headers

#### Scenario: Reading back recorded targets

- **WHEN** a test issues `POST /rate?value=0` and `PUT /setProperty?forwardEndTime`
- **THEN** the recordings expose the two methods and the two full request targets, including query strings, in the order they were received

### Requirement: Legacy digest challenge control

The legacy mode SHALL be configurable to require digest authentication, to reuse a challenge until a correct credential arrives, and to reject a correct credential on demand, and it MUST report whether a `401` was caused by a missing credential or by a wrong one.

```ruby
Airplay::FakeDevice::Receiver.new(
  legacy: { digest: { realm: "AirPlay", nonce: "n", qop: true,
                      username: "Airplay", password: "pw" } }
).start
# receiver.digest_missing, receiver.digest_wrong, receiver.digest_attempts
```

#### Scenario: Challenge then success

- **WHEN** the mode is set to require digest and receives a request with no `Authorization` header followed by one carrying the expected response
- **THEN** it answers `401` with a `WWW-Authenticate: Digest` challenge first, then the scripted success, and reports exactly one request as missing a credential

#### Scenario: Wrong credential is distinguished from a missing one

- **WHEN** the mode receives a request whose `Authorization` header carries a response computed from the wrong password
- **THEN** it answers `401` with a fresh challenge and reports that attempt as having a wrong credential rather than a missing one

#### Scenario: Correct credential rejected on demand

- **WHEN** the mode is configured to reject authentication and receives a request carrying the response it would otherwise accept
- **THEN** it answers `401` without accepting the request
