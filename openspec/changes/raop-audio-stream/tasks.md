# Tasks

## 1. RTP transport and payload sealing

- [ ] 1.1 Add the session-scoped audio timeline state (payload type, SSRC, sequence number, RTP timestamp, frame size) to the session model, so a stream owns its numbering instead of the transport module; verify with a unit test that two concurrently created sessions get independent sequence numbers, timestamps and SSRCs.
- [ ] 1.2 Implement packet sealing (`lib/airplay/raop/sealing.rb`): ChaCha20-Poly1305 with the session's 32-byte stream key, the packet's RTP timestamp and SSRC as additional authenticated data, a 12-byte nonce whose first four bytes are zero, and a trailer of the 16-byte tag followed by the transmitted eight nonce bytes; verify with fixed vectors plus a round-trip decrypt, and with a case that fails when the tag and nonce are assembled in the wrong order.
- [ ] 1.3 Derive the transmitted nonce per stream type: the RTP sequence number for realtime streams and a monotonically increasing per-packet counter for buffered streams; verify with a unit test that a re-sent realtime packet is byte-identical to its original and that a 100 000-packet buffered run never repeats a nonce.
- [ ] 1.4 Implement the realtime datagram transport: bind a local socket, send to the receiver's negotiated data port, set the marker bit on the first packet after record and after a flush, and never block the reactor on a send; verify with a loopback socket test asserting destination port, marker placement and a non-blocking send under a full send buffer.
- [ ] 1.5 Implement the bounded retransmission backlog (ring over the most recent packets) and the control-port request handler that answers with the byte-identical original; verify with a unit test that a held sequence number is resent byte for byte, an evicted one is reported as a miss, and the retained count never exceeds the bound.
- [ ] 1.6 Implement the buffered transport: connect to the negotiated data port, frame each packet with the two-byte big-endian length that counts itself, and park unwritten bytes when the socket cannot accept them; verify in the protocol lane with a double that stops reading for several seconds and then resumes, asserting no error, contiguous frames and no sequence gap.
- [ ] 1.7 Implement stream teardown for the transport: close both transports and the timing responder, release the local ports and wipe the stream key; verify with a test that rebinding the released ports succeeds immediately and with an assertion that no reference to the key survives on the session.
- [ ] 1.8 Land the group's tests and its reference material: unit tests for the timeline, sealing, nonce derivation and backlog under `test/unit/raop/`, plus the audio wire-format section of the protocol reference page (packet layout, trailer order, nonce derivation, backlog bound) whose examples are the same constants the vector suite executes.

## 2. PCM source and framing

- [ ] 2.1 Define the PCM source interface the sender pulls frame chunks from (chunk size, sample rate, channels, byte width, `read_frames(n)` returning a final short chunk at EOF) and implement the raw PCM reader against it; verify with a unit test that chunk boundaries follow the requested frame count and that a final partial chunk is returned unmodified.
- [ ] 2.2 Implement the WAV reader natively (RIFF header parse, 16-bit PCM, mono/stereo, 44.1 kHz and 48 kHz) with no external dependency; verify with fixtures under `test/fixtures/` and a unit test asserting format detection and frame-count accuracy.
- [ ] 2.3 Implement the `ffmpeg`-backed decode edge for inputs the native reader cannot open, feeding the same PCM source interface, and make its absence a normal path rather than an error; verify with a unit test that the WAV lane runs with `ffmpeg` absent from `PATH` and that the decode lane is marked skipped with the missing dependency named when it is.
- [ ] 2.4 Implement packet assembly from the source: pad the final short chunk with silence to a whole packet, keep the frame count in the RTP timestamp, and drain the remaining lead with silence packets at end of input so announcements stay in line; verify with a unit test that the padding keeps the timeline continuous and that end-of-input padding carries zeros.
- [ ] 2.5 Land the group's tests and its reference material: unit tests for both readers, the padding rules and the decode-edge gating, plus the input-format section of the usage page listing which formats take the native lane and which take the decode edge.

## 3. Two-phase setup and stream negotiation

- [ ] 3.1 Implement phase one: build the binary-plist body with device identity in device-ID and MAC form, a fresh session UUID, our timing responder's port and the timing protocol the session can serve, and parse the reply (event port, timing port); verify with a protocol-lane test asserting the request's fields on the paired channel and that no stream definition, codec or key appears in it.
- [ ] 3.2 Implement phase two: build the single stream entry (payload type, compression type, format descriptor, sample rate, frames per packet, control port, stream key, and latency bounds for realtime streams only) and read the reply's ports by key; verify with a protocol-lane test whose double serializes its control port before its data port and still gets audio on the data port, plus a reply without a data port that fails the binding with a coded error.
- [ ] 3.3 Implement codec selection bounded by the receiver's codec list: prefer uncompressed PCM, take ALAC only when PCM is absent, ALAC is advertised and an encoder is available, and otherwise fail with a coded unsupported-codec error; verify with protocol-lane runs for the PCM lane, the ALAC-gated lane and the empty-codec-list lane.
- [ ] 3.4 Implement stream-type selection from the receiver's buffered-audio advertisement and the session's established timing route, record the decision (type and payload type) on the session before phase two, and refuse to send a stream definition that disagrees with the record; verify with tests for the buffered-capable route on an NTP session (realtime, reason recorded), the established route (buffered) and a constructed mismatch that is refused before the request leaves the sender.
- [ ] 3.5 Implement per-session stream-key handling: generate 32 bytes per session, carry them only in the phase-two definition, keep them out of logs and the credential store, and forget them at teardown; verify with a test asserting two sessions get different keys and that the emitted logs and credential store contain no value equal to either key.
- [ ] 3.6 Implement the RAOP-compat handshake path (SDP announcement, setup with a transport header advertising our control and timing ports, receiver ports read from the reply) feeding the same parameter set into the audio engine; verify with a protocol-lane test in the double's legacy mode asserting announcement-before-setup ordering and the ports used for audio and control.
- [ ] 3.7 Implement the lifecycle commands (record, realtime flush with the last sequence and timestamp, buffered flush with the buffered equivalents, teardown) with record required before the first audio packet and every non-success answered with a coded error naming the command; verify with protocol-lane tests asserting the recorded command order, the flush payloads, and that a rejected record sends no audio.
- [ ] 3.8 Implement the coded-error mapping for the setup path (rejected phase, missing data port, unsupported codec, rejected lifecycle command) into the shared taxonomy; verify with tests that each failure surfaces a distinct code and that a rejected phase two still allows a retry on the same control session.
- [ ] 3.9 Land the group's tests and its reference material: the protocol-lane setup suite (ordering, by-key parsing, codec and type selection, key hygiene) and the setup section of the protocol reference page documenting both handshakes and the fields each carries.

## 4. Timing responder and time announcements

- [ ] 4.1 Implement the UDP timing responder on the port advertised in phase one, answering each well-formed request with the requester's send timestamp echoed as the reference timestamp and our receive and transmit timestamps, all in NTP-epoch 64-bit fixed point; verify with a unit test on the reply fields and a protocol-lane test where the double times a session successfully.
- [ ] 4.2 Implement the NTP conversions and timeline arithmetic (wall clock to NTP, timeline position to timestamp and back, using the session's sample rate); verify with a vector set that round-trips known positions within one frame and pins the NTP epoch offset.
- [ ] 4.3 Implement the announcement ticker: at least one announcement per second to the receiver's control port carrying the wall-clock instant, the position audible at it and the send head position, with the first announcement of a run marked and sent before that run's first audio packet; verify in the protocol lane that a ten-second run yields at least ten announcements, that the first of each run is marked, and that consecutive announcements extrapolate along one line within tolerance.
- [ ] 4.4 Implement the frozen anchor line so announcements extrapolate from the anchor instead of the send head, and pin it with a test where the send head races ahead while the buffer fills and the announcements still agree.
- [ ] 4.5 Implement the untimed-receiver detection window and its reported state, with a late exchange clearing the state; verify with protocol-lane runs against a silent double (state reported as not established within the window) and a double that answers after the window (state established, scheduled start proceeds).
- [ ] 4.6 Harden the responder against malformed input (short or unrecognizable datagrams produce no reply and do not end the session); verify with a unit test feeding truncated and garbage datagrams followed by a valid request that is answered.
- [ ] 4.7 Land the group's tests and its reference material: the timing-lane suite (reply fields, announcement cadence, frozen line, untimed detection) and the timing section of the protocol reference page (request and reply layout, announcement layout, epoch and conversion rules).

## 5. Anchor, pacing and flush re-anchoring

- [ ] 5.1 Thread the session's injected clock through the anchor, pacing, announcement and readiness code so no timeline arithmetic reads the system clock directly; verify with a code-level test that injects a clock and drives a frame release without real waiting.
- [ ] 5.2 Implement the anchor computation: a commanded instant clamped to a lead inside the receiver's reported latency window (default inside the standard two seconds when nothing is reported), a minimum lead of 250 ms, and a forward correction with the corrected instant reported when the commanded instant is unreachable or in the past; verify with tests for an exact instant, a past instant and an instant inside the minimum lead.
- [ ] 5.3 Implement the paced send loop: release each frame at its release point, keep delivery inside the pacing window, catch up by sending additional frames when behind, and drop no content; verify in the protocol lane with the harness clock for window compliance, for catch-up after a source stall with sequence and timestamp continuity, and for a slow sink that produces no further sends while the clock is held still.
- [ ] 5.4 Implement the pacing window from the receiver's reported latency (clamped when reported, conservative default otherwise, assumption recorded) and keep a reported downstream render latency informational only; verify with tests for a clamping reply, a reply with no window, and a reply carrying a render latency whose anchor stays unchanged.
- [ ] 5.5 Implement flush re-anchoring: discard positions the receiver no longer holds, fix a new anchor line, send a marked announcement for it before any new audio, keep the stream key and continue sequence numbering; verify in the protocol lane that the first packet of the new run is at or after the new anchor and that sequences continue without a restart.
- [ ] 5.6 Implement the not-before-anchor rule and its coded outcomes: content is never delivered before its anchor, an unseatable start is corrected forward or fails with a coded timing error, and silence is never sent in place of content to fake a start; verify with a protocol-lane run against an untimed double asserting no content was delivered for the elapsed instant and a coded timing error was reported.
- [ ] 5.7 Land the group's tests and its reference material: the pacing suite (window compliance, catch-up, frozen clock, starvation floor) and the anchor-and-pacing section of the protocol reference page, including the tolerance and the default window the harness asserts against.

## 6. Volume and the audio metadata surface

- [ ] 6.1 Implement the volume curve (percentage mapped linear-in-dB onto −30..0 dB, zero sent as the ecosystem's muted value), the parameter request that carries the mapped value, and the no-local-gain rule; verify with unit vectors for 100/50/0 percent, a protocol-lane assertion that the double records the mapped value, and a check that identical content produces identical ciphertext at two different volumes.
- [ ] 6.2 Implement DMAP text metadata (title, album, artist as tagged fields in a DMAP container with the DMAP content type), sent only when the receiver advertises text metadata; verify with a protocol-lane test asserting the container shape and the tagged fields, and a double that advertises nothing receiving no metadata request.
- [ ] 6.3 Implement artwork as an image parameter carrying the session's current sequence number and RTP timestamp, and progress as a start/now/end parameter on the session timeline, each gated on the advertised metadata type; verify with protocol-lane tests asserting the headers, the image content type and that progress values advance with the timeline.
- [ ] 6.4 Land the group's tests and its reference material: the parameter-surface suite (curve vectors, DMAP shape, artwork headers, progress gating) and the volume-and-metadata section of the usage page documenting the slider-to-dB behaviour and which receivers see which metadata.

## 7. Group playback and the release barrier

- [ ] 7.1 Implement group membership over sessions: at most one session per device, reuse of an existing session when the device is added again, and refusal with a coded error when another group owns the device; verify with unit tests for all three cases.
- [ ] 7.2 Implement the group start barrier: choose one shared instant, bind and anchor every member against it, and release only when every member has a bound, anchored stream; verify with a unit test using the injected clock that no member writes content before the barrier releases and that a fast member's first sample is still anchored to the shared instant.
- [ ] 7.3 Implement the per-session timeline offset (session-derived initial sequence number and RTP offset) recorded on the member's anchor and absorbed by the anchor line; verify with a protocol-lane group run asserting two members of identical content differ in sequence numbering and offset while anchoring the same content sample to the shared instant.
- [ ] 7.4 Implement the 50 ms tolerance verdict: report a start as synchronised only when every member's reported audible instant is within the tolerance, and otherwise name the offending member with the instant it used; verify with unit tests for an aligned group and a member 120 ms late.
- [ ] 7.5 Implement member-failure reporting (a member that cannot bind, cannot be timed or fails mid-start is reported with its coded error, the group result is at most partially successful) and completion driven by each session's drain state; verify with unit tests for each failure and a completion test that finishes with the clock held still, proving no interval poll remains.
- [ ] 7.6 Rework `lib/airplay/group.rb` and `lib/airplay/group/players.rb` onto the barrier and session-state completion, deleting the `sleep 0.1 while still_playing?` wait; verify that no source file under `lib/airplay/group/` contains an interval-based wait and that the group unit suite passes.
- [ ] 7.7 Land the group's tests and its reference material: the group suite (membership, barrier, offsets, verdict, completion) and the group section of the usage page documenting the shared start, the tolerance and the per-member reporting.

## 8. Audio harness on the virtual receiver

- [ ] 8.1 Implement the receiver double's audio transports: a datagram socket for realtime streams and a stream listener for buffered streams, both bound to the ports the double returns in its stream setup reply; verify with a lane run that reports the ports it advertised and receives the session's audio on exactly those ports.
- [ ] 8.2 Implement the decrypting sink with its per-session assertions (sequence continuity, timestamp advance against frames carried, constant non-zero SSRC, declared payload type, marker on the first packet of a run only, trailer order of tag then nonce, authentication of the timestamp and SSRC) and report every failure with the offending packet; verify by running the sink against a conforming session with no failures and against fixtures that swap the trailer order and alter a timestamp, which must fail with the named assertion.
- [ ] 8.3 Implement the fault knobs (drop a run of packets, duplicate, delay, reorder, stop reading a buffered stream and resume, withheld timeline acceptance) selectable per session and reported in the run result; verify that a dropped run provokes a retransmission the sink recovers, that reordering does not break the sink, and that a multi-second read pause completes cleanly.
- [ ] 8.4 Implement the pacing assertions against the injected clock (delivery instant per packet, failing a run that runs ahead of the window, misses a deadline, or keeps delivering while the clock is held still); verify by running a conforming session to a pass and a deliberately unthrottled sender fixture to a failure.
- [ ] 8.5 Implement the timing modes on the double (answer, stay silent, refuse the announced timeline) with the control session still accepted in silent mode; verify that the answering mode reports a timed session, the silent mode reports the sender's not-established outcome, and the refusal mode reports the sender's coded timing outcome.
- [ ] 8.6 Implement the multi-room run: several doubles on one host, one group start, a failure when any two first audible instants differ by more than the tolerance with the offending members named, and every member's instant reported; verify with an aligned run that passes and a skewed run (one double delaying its content) that fails and names the member.
- [ ] 8.7 Land the conformance vectors that need no receiver: sealing cases with fixed key, nonce, additional authenticated data and expected ciphertext with tag, the trailer assembly case that pins tag-before-nonce, the announcement field layout, and the timeline/NTP conversion cases; verify by executing the vector suite with no receiver bound.
- [ ] 8.8 Implement the codec and stream-type lanes on the double (configurable codec list, stream-type reply) and the skip reporting when no ALAC encoder is available; verify with the PCM lane reporting the declared compression type and format, the empty codec list reporting the sender's coded error with no audio received, and the ALAC lane reporting itself skipped with the missing dependency named.
- [ ] 8.9 Implement the control and parameter recording on the double (lifecycle commands in order, volume parameter, DMAP metadata, artwork with its RTP information, progress) and expose it to tests; verify that the recorded order shows record before the first audio packet and that the recorded parameter values match the sender's mapped values.
- [ ] 8.10 Land the group's tests and its reference material: self-tests that drive the harness against known-bad sender fixtures (a swapped trailer, an unthrottled pacer, an unmarked first packet, a duplicate-nonce stream) and assert the harness fails each with the right assertion, plus the harness section of the testing page (knobs, lanes, vector names).

- Archive ordering: archive `runtime-async-reset` first (session facade, error taxonomy, injectable clock, test lanes, receiver-double package), then `mdns-discovery` (the capability model the codec and stream-type decisions read), then `airplay2-pairing-control` (it creates `airplay2-control-channel` and `route-selection`, whose main specs must exist before this change's deltas can be applied) and `airplay1-legacy-sender` (the RAOP-compat HTTP and digest client the compat handshake reuses). Only then archive this change, so its three `ADDED` deltas to sibling-owned capabilities land on specs that already exist; `airplay2-video-playqueue` is independent of that ordering.
