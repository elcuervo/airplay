# Spec Delta

## ADDED Requirements

### Requirement: Play Queue Harness receiver mode

The virtual receiver MUST provide a play-queue mode that accepts the encrypted control channel,
registers a URL control stream and answers the command endpoint, and it MUST record every request it
receives with its method, path, headers and decoded binary-plist body for assertion.

#### Scenario: Mode drives a play

- **WHEN** a test starts the receiver in play-queue mode and replays a recorded play against it
- **THEN** the recorded exchanges expose the control-stream `SETUP` and each `POST /command` request with its decoded payload, without avahi or physical hardware

#### Scenario: Recorded traffic is readable after the fact

- **WHEN** a test asks the mode for the exchanges it recorded
- **THEN** it receives them in arrival order and can match each one against an expected request

### Requirement: Play Queue Harness exact-order assertions

The mode MUST accept an expectation list of requests and MUST fail the assertion when order, method,
path, headers or decoded payload differ, and it MUST answer a command body that is not wrapped as the
protocol requires with a client error.

#### Scenario: Out-of-order commands fail

- **WHEN** a sender issues the play-queue commands in an order other than the expectation list
- **THEN** the assertion fails at the first divergence and names the differing request

#### Scenario: Deviating but unasserted traffic is visible

- **WHEN** a sender emits a request the expectation list does not contain
- **THEN** the extra request is reported rather than ignored

#### Scenario: Unwrapped command body is refused

- **WHEN** a request carries the command as a top-level plist instead of a nested binary plist
- **THEN** the mode answers with a client error

### Requirement: Play Queue Harness scripted event transitions

The mode MUST be able to push scripted event-channel transitions on demand from a test — including
playing followed by loading followed by playing, playing to paused, playing to stopped, and a device
that never transitions — and MUST be able to answer playback-info from a script.

#### Scenario: Transition scripts are triggered by the test

- **WHEN** a test triggers a scripted transition
- **THEN** the sender observes exactly that state and the trigger order is preserved

#### Scenario: A device that never transitions

- **WHEN** the mode is configured to report nothing on the event channel
- **THEN** the sender's startup window expires and its did-not-start path is exercised

#### Scenario: playback-info scripts

- **WHEN** a test configures playback-info answers, including an empty answer and an error answer
- **THEN** the sender observes the configured answers in order

### Requirement: Play Queue Harness replay fixtures

Replay fixtures for this route MUST be committed captures, or derivations of an external reference
implementation, and MUST record their provenance — the reference and the firmware they came from —
so a test can compare a sender's request against them byte for byte.

#### Scenario: Fixture provenance is recorded

- **WHEN** a fixture is read by a test
- **THEN** its provenance names the source capture or reference implementation and the firmware version it was observed on

#### Scenario: Fixtures are not generated by the implementation

- **WHEN** a fixture-comparison test runs
- **THEN** the expected bytes come from the committed fixture, not from the code path under test

### Requirement: Play Queue Harness fault knobs

The mode MUST support per-test faults for this route: a transient `500` on a chosen command, `401`
and `403` statuses, a refused control stream, a failure after the item was inserted, a connection
drop when the setup ordering is violated or feedback overlaps a command, and a delayed or absent
event-channel answer.

#### Scenario: Each fault is selectable per test

- **WHEN** a test configures one of these faults
- **THEN** only the requests of that test observe it and the sender's documented path for that fault is exercised

#### Scenario: Partial application is reproducible

- **WHEN** the mode is configured to accept the item insert and then fail a later command
- **THEN** the insert is recorded exactly once, so a duplicate insert is detectable

### Requirement: Play Queue Harness media fetch

The mode MUST be able to act as a client of the sender's media server, fetching a URL it was handed
and recording the requests it made — path, method and any byte range — so both the served contract
and the handed URL can be asserted in one test.

#### Scenario: Handed URL is fetched from the receiver side

- **WHEN** a test drives a local-file play and asks the mode to fetch the handed URL including a byte range
- **THEN** the mode records those requests and the responses it received, and the test asserts the served content type, length and partial-content answer

#### Scenario: A URL the sender does not serve

- **WHEN** the handed URL is not served by the sender's media server
- **THEN** the mode records the failed fetch instead of failing the test in the transport

### Requirement: Play Queue Harness hardware lane

The opt-in hardware lane MUST cover this route with a remote HLS stream, a locally served HLS stream
and a locally served progressive file, MUST record per run the device model, firmware version, timing
mode, profile used, observed state sequence, event count and outcome, and MUST skip cleanly when no
device is configured.

#### Scenario: No device configured

- **WHEN** the hardware lane runs with no receiver configured
- **THEN** these scenarios report skips with a reason and the lane exits successfully

#### Scenario: Observation is recorded per run

- **WHEN** the lane runs against a configured device
- **THEN** its output names the model, firmware version, timing mode, profile, the states observed and the outcome of each of the three media scenarios

#### Scenario: Route comparison on hardware

- **WHEN** the same device is driven through the modern route and with the legacy route forced
- **THEN** the recorded outcomes distinguish the two routes and name the one that delivered playback
